# AI Model Evaluation - Meal Plan Generator

This document contains my evaluation of the recipes and meal plans generated by the `LlmProxy` project using OpenAI's `gpt-4o-mini` model. I have evaluated the outputs across three iterations to see how prompt engineering changes the quality of the data.

---

## 1. What is a "Good Output"? (My Criteria)

To know if the AI did a good job, I measured the results against these simple criteria:
* **Relevant for the user:** The menu must actually follow the user's preferences and family situation.
* **Nutritious & healthy:** The menu should try to follow health guidelines like the Nordic Dietary Recommendations (NNR) with good variation.
* **Correct format:** The AI must return raw, valid JSON matching my C# system prompt, without any markdown text (like ` ```json `) or extra conversational chatter, so the backend can parse it without crashing.
* **Clean data:** The measurement units should be structured and consistent so they can be saved cleanly in the database.

## 3. Conclusion
**When is the AI service good to use?**
The AI does a great job of coming up with creative recipes based on a prompt. During these tests, it became very clear that the more specific and detailed you are in your prompt, the better and more accurate the weekly menu becomes. Writing the prompt in one single language and setting strict boundaries is very important if you want to avoid unstable data.

**When is it not suitable?**
You cannot trust the AI to do perfect math or follow strict database constraints 100% of the time. It easily slips back into standard recipe habits (like 4 portions or using tbsp).
Therefore, things like scaling portions, validation, and data cleaning are best handled by C# code in the backend, rather than trying to make the prompt perfect.
